# Fiscal ARCA Protocol Specification

## Purpose

The protocol boundary between Ways and ARCA (ex-AFIP): how a TRA becomes a signed CMS, how the
Access Ticket (TA) is obtained and cached, the hand-rolled SOAP 1.1 envelope, the WSFE operation
surface, the fixture suite that embodies the official manual as an executable contract, and the
ARCA error taxonomy. Nothing here calls a real ARCA server (19a scope: mocks only).

## Requirements

### Requirement: TRA Generation And CMS Signing Use BCL Only

The system MUST build a `LoginTicketRequest` (TRA) XML per the WSAA spec and sign it into a CMS
(PKCS#7) using `System.Security.Cryptography.Pkcs.SignedCms` exclusively — no third-party crypto
library. The signing certificate for tests MUST be generated at runtime by the test itself
(`CertificateRequest`, BCL); no `.pfx`/`.pem`/`.key` or base64 key material MAY ever be committed.

#### Scenario: A TRA is signed into a valid CMS with a runtime-generated certificate
- GIVEN a self-signed X.509 certificate generated by the test via `CertificateRequest`
- WHEN the TRA is signed
- THEN the resulting CMS verifies against that certificate's public key with no external dependency

#### Scenario: No key material exists anywhere in the repository
- GIVEN the full `src/` and `tests/` trees
- WHEN a repository-wide scan runs for PEM/PFX/private-key markers
- THEN it finds zero matches

### Requirement: The Access Ticket Is Cached In Memory Behind A Port, TTL Bound By IRelojDelSistema

`IRepositorioDeTicketDeAcceso` MUST cache the TA keyed by `(empresa, ambiente, servicio)` for 12
hours minus a safety margin, using `IRelojDelSistema` as the only time source — never `DateTime.Now`.
A cached, still-valid TA MUST be reused without issuing a new `LoginCms`. Persistent (DB-backed)
storage of the TA is out of scope for 19a (registered 19b gate item, decision 10).

#### Scenario: A cached valid TA is reused without a new login
- GIVEN a TA obtained at `T` with `RelojFijo` pinned at `T`
- WHEN a request needs a TA at `T + 11h`
- THEN the cached TA is used and `LoginCms` is not invoked again

#### Scenario: The TA is renewed exactly at its expiry boundary
- GIVEN a TA cached at `T` and `RelojFijo` advanced to `T + 12h + 1s`
- WHEN a request needs a TA
- THEN the cache reports expired and a new `LoginCms` is issued

### Requirement: SOAP 1.1 Envelopes Are Hand-Rolled And Isolated In One File

`SobreSoap` MUST be the only file in the codebase that knows SOAP exists, building envelopes over
`HttpClient` + `System.Xml.Linq`. `System.ServiceModel.Http` and any WSDL-generated proxy MUST NOT
be used (decision 7).

#### Scenario: The generated FECAESolicitar envelope matches the manual byte-for-byte
- GIVEN a reference invoice request built from a fixed set of inputs
- WHEN `SobreSoap` serializes the `FECAESolicitar` envelope
- THEN it is byte-for-byte identical to the golden XML transcribed from the manual's example

### Requirement: The WSFE Client Exposes Exactly The Manual's Operation Surface

`IClienteWsaa` / `IClienteWsfe` MUST expose `LoginCms`, `FECAESolicitar`, `FECompConsultar`,
`FECompUltimoAutorizado`, `FEParamGetTiposCbte`, `FEParamGetTiposIva`, and
`FEParamGetCondicionIvaReceptor` — no other ARCA operation is implemented in 19a.

#### Scenario: FECompUltimoAutorizado returns 0 for a never-used series
- GIVEN a `(PtoVta, CbteTipo)` pair with no prior authorization in the fixture
- WHEN `FECompUltimoAutorizado` is called
- THEN the response's `CbteNro` is `0` — a legal "series never used" answer

### Requirement: The Fixture Suite Embodies The Manual And Is Pinned To Its Revision

Every fixture file MUST name the manual section it transcribes, and the fixture set MUST be pinned
via `REVISION.md` to `manual-desarrollador-ARCA-COMPG-v4-0.pdf` (RG 4291, rev. 15/01/2025) and
`Especificacion_Tecnica_WSAA_1.2.2.pdf` (decision 8). Minimum contents: `LoginTicketRequest`/
`LoginTicketResponse`, the `FECAESolicitar` golden request plus its three responses (approved,
approved-with-observations, rejected), `FECompConsultar` found/not-found, `FECompUltimoAutorizado`
head and empty-series, and the full error taxonomy.

#### Scenario: The three FECAESolicitar responses are distinct fixtures
- GIVEN the fixture directory
- WHEN it is inspected for `FECAESolicitar` responses
- THEN exactly three exist: approved (CAE, no observations), approved-with-observations (CAE +
  `Observaciones[]`), and rejected (no CAE, an excluding validation error)

### Requirement: ARCA Errors Map To A Named Domain Error Taxonomy

The client MUST map WSAA fault codes `500/501/502/600/601/602` and WSFE `Errors[]` /
`Observaciones[]` entries — including `10016` (non-correlative number) — to named domain errors,
never a generic exception.

#### Scenario: A non-correlative number fixture proves invariant I1's failure mode
- GIVEN a `FECAESolicitar` fixture returning WSFE error `10016`
- WHEN the client parses the response
- THEN it raises a named `numero_no_correlativo` domain error, and the fiscal number stays bound to
  the `pendiente` comprobante — it is not released

### Requirement: No Real ARCA Endpoint Is Ever A Configuration Default

No configuration file shipped to `main` in 19a MAY carry `wswhomo.afip.gov.ar` or
`servicios1.afip.gov.ar` as a default value. Reopen condition: 19b.

#### Scenario: A configuration scan finds no real ARCA hostname
- GIVEN every configuration file merged to `main` in this sub-stage
- WHEN it is scanned for `afip.gov.ar` hostnames
- THEN none is found as a default value
