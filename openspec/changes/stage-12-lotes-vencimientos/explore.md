# Exploration: Stage 12 — Lotes y Vencimientos (FEFO)

## Current State

### 1. Stock model (today, no lot dimension)

- `src/Ways.Domain/Stock/Stock.cs` — PK-only cache `(id_articulo, id_punto_venta)`, `Cantidad numeric(12,3)`, `Minimo`/`Reposicion` nullable. `IdTenant` is a plain non-key column (manual RLS filter), no CHECK on `Cantidad` (negative allowed). Written exclusively via `INSERT ... ON CONFLICT (id_articulo, id_punto_venta) DO UPDATE SET cantidad = stock.cantidad + $delta RETURNING cantidad` (row-lock-as-serialization pattern, doc 10 §6, design decision 1).
- `src/Ways.Domain/Stock/MovimientoStock.cs` — append-only ledger, no `EntidadBase`/`EntidadTenant` (hand-rolled `IdTenant` + manual RLS filter, `creado_el` not `created_at`). Columns: `Id, IdTenant, IdArticulo, IdPuntoVenta, Cantidad (signed), Motivo (enum motivo_stock: venta|compra|anulacion|ajuste|transferencia|inventario), IdComprobanteVenta?, IdComprobanteCompra?, IdPuntoVentaDestino?, IdEmpleado, Observaciones?, CreadoEl`. CHECK `ck_movimientos_stock_cantidad_no_cero`.
- Doc reference: `docs/10-modelo-de-datos.md` §6 (lines 505-559) — table shapes, and the historical annotations at lines 526-555 documenting which motivo values got writers in which stage.
- **Invariant that any lot design must preserve** (`openspec/specs/stock/spec.md`, "Cantidad Is Always The Sum Of Its Movimientos"): `stock.cantidad` per `(id_articulo, id_punto_venta)` MUST equal `SUM(movimientos_stock.cantidad)` for that pair across all six existing motivos — this is asserted by tests today and any lot-scoped ledger addition must not break it (aggregate cache still keyed by articulo+PV, independent of lot).
- **Structural fact — three independent raw-SQL write sites, no shared helper**: `ServicioDeVentas`, `ServicioDeCompras`, and `ServicioDeStock` each carry their OWN private copies of `InsertarMovimientoStockAsync`/`UpsertStockAsync` (raw ADO, not EF `SaveChanges`) — `ServicioDeCompras`'s doc-comment explicitly states this duplication is deliberate ("`ServicioDeStock`/`ServicioDeVentas` NO se tocan — Slice 2 non-negotiable... duplicados a propósito"). A lot-dimension column added to `movimientos_stock`/`stock` requires touching all three files' raw statements independently — there is no single choke point.

### 2. Sale emission (stock decrement)

- `src/Ways.Application/Ventas/ServicioDeVentas.cs`, `EmitirAsync`/`EjecutarTransaccionAsync` (lines 606-720). "Decide, then commit" split: everything that reads/validates (pricing, ofertas, parametros, payment validation) runs BEFORE the transaction and freezes an immutable `PlanDeVenta`; the transaction only writes, in this pinned order (design: The Sale Transaction):
  0. turno re-check under `FOR SHARE` (first statement)
  1. numeración (already committed in its own prior transaction)
  2. comprobante header
  3+4. items + pagos (single `SaveChangesAsync`)
  5. **stock — ascending order by `id_articulo`** (non-negotiable anti-deadlock order, design decision 2): `foreach (var item in plan.Items.Where(i => i.EsProducto).OrderBy(i => i.IdArticulo))` → `InsertarMovimientoStockAsync` (motivo=Venta) + `UpsertStockAsync`. Services (`EsProducto = false`) are skipped entirely — no movement, no stock row.
  6. cuenta corriente (one payment at a time, in request order)
- Same file also handles anulación (`EjecutarAnulacionAsync`, ~line 374+): inverse movement per original item, ascending `id_articulo` too, same lock discipline. **Anulación iterates the ORIGINAL comprobante's own item rows** — so it always knows exactly which item (and, if a lot dimension were added there, which lot) to reverse.
- `ItemComprobanteVenta` (`src/Ways.Domain/Ventas/ItemComprobanteVenta.cs`) is an immutable snapshot (doc 10 principle 6) — `IdArticulo`, `Cantidad` (signed: positive TX, negative NCX), `CostoUnitario`, etc. **No lot/batch reference field exists today.**
- Credit notes (devoluciones) are NOT a separate entity/table. `openspec/specs/comprobantes-venta/spec.md` → "Devoluciones As NCX Comprobantes": a devolución is an ordinary comprobante of `tipo NCX` (`signo` negative) emitted through the SAME `EmitirAsync`/`EjecutarTransaccionAsync` path, with negative-quantity lines that flow through the same ascending-`id_articulo` stock loop (net effect: positive delta = stock re-enters). `id_comprobante_asociado` is optional, so an NCX is **not required** to reference the original sale. This is critical evidence for the "how does lote interact with notas de crédito" open decision: today there is no mechanism to know which physical lot a returned unit came from unless the NCX line explicitly carries that information (client input or derived from a mandatory `id_comprobante_asociado` + original item lookup).

### 3. Purchase reception (stock increment)

- `src/Ways.Application/Compras/ServicioDeCompras.cs`, `ConfirmarAsync`/`EjecutarConfirmarAsync` (lines 243-382). Compras have a real state machine (`EstadoCompra`: Borrador → Confirmada → Anulada), unlike transfers. `ConfirmarAsync`:
  1. `UPDATE ... RETURNING` on the header — single authority for the Borrador→Confirmada transition, row lock serializes concurrent confirms.
  2. reads `ItemComprobanteCompra` rows (`OrderBy(i => i.IdArticulo)`) — read set frozen under the header lock.
  3. **one movimiento + upsert of stock per item, ascending `id_articulo`** — `MotivoStock.Compra`, `id_comprobante_compra` populated.
  4. `costo_nominal` update on `articulos` (dedup, highest `orden` wins) — separate from stock loop.
- `ItemComprobanteCompra` (`src/Ways.Domain/Compras/ItemComprobanteCompra.cs`): `IdArticulo NOT NULL` (a purchase line without articulo can't move stock — it's a gasto instead), `Cantidad` (derived: `unidades + bultos × unidadesPorBulto`), `CostoUnitario numeric(14,4)`. **No lot/expiry fields today** — this is the natural landing spot for `fecha_vencimiento`/lote-per-line input at reception time.
- Anulación (`openspec/specs/comprobantes-compra/spec.md` → "Anulación Reverses By Contramovimientos"): reverses ALL items' full quantity; refused with `409 compra_anulacion_stock_negativo` if any resulting cache would go negative (goods already sold can't be pulled back). Since compra items map 1:1 to lot-creation-at-receive-time, an anulación reversing a specific lot's remaining balance is structurally straightforward — but the "already sold" refusal logic would need to become lot-aware (or stay aggregate-level, which is looser).

### 4. Transfers between points of sale

- `src/Ways.Application/Stock/ServicioDeStock.cs`, `TransferirAsync`/`EjecutarTransferenciaAsync` (lines 81-178). **No dedicated header entity/table, no state machine, no in-transit state** — confirmed both by code (no `Transferencia` class found anywhere in `src`) and by spec (`openspec/specs/transferencias-de-stock/spec.md`, Purpose: "no in-transit state, ... no separate transfer document MUST exist — the transfer completes or it does not happen at all"). A transfer of N lines writes exactly `2N` `movimientos_stock` rows (motivo=Transferencia, mirrored: origin negative / destination positive, `id_punto_venta_destino` set) in one transaction.
- Design decision 9 (mission-critical lock discipline): builds ONE ascending total order over the `2N` keys `(id_articulo, id_punto_venta)` — never "all origin, then all destination" — this is what prevents deadlock against a reverse simultaneous transfer or a concurrent checkout (which already orders its own stock upserts ascending by `id_articulo`).
- Back-office tightening (asymmetric vs. checkout): a transfer that would leave the origin negative is refused with `409 stock_insuficiente_para_transferencia` — the `RETURNING` of the upsert itself is the sufficiency check (no second query, no TOCTOU).
- A lot dimension here needs to decide: does a transfer let the operator pick which lot(s) to move (FEFO-suggested), or does it move an aggregate quantity and let the destination re-bucket into an "unidentified" lot? The existing lock-order discipline (2N keys, ascending) would need to extend to `(id_articulo, id_punto_venta, id_lote)` tuples if lot becomes part of the transfer unit.

### 5. Inventory count / adjustments (the circuit Stage 12's "decomiso" extends)

- `ServicioDeStock.AjustarAsync` (manual ajuste, admin-only, requires non-empty `observaciones`) and `ContarAsync` (conteo: client sends the TOTAL counted, never a delta — server derives the delta under the same row lock used by ajuste, motivo=Inventario). Both are single-item, single-PV operations; conteo explicitly forbids a client-supplied delta and writes NOTHING when the count matches (avoids the `cantidad <> 0` CHECK).
- Both are strictly aggregate-level today (no lot breakdown). Stage 12's decomiso-por-vencimiento is explicitly framed in doc 11 as "circuito de ajuste ... por vencimiento con su movimiento de stock correspondiente" — i.e., it is meant to reuse this same shape (a typed ajuste), which means the natural extension is either a new `MotivoStock` value (`Decomiso`) or a sub-reason on top of `Ajuste`, PLUS a mandatory `id_lote` parameter that today's `AjustarAsync` signature does not have.
- `openspec/specs/conteo-de-inventario/spec.md` explicitly scopes out "any full-count snapshot/freeze/variance workflow" — conteo is per-articulo only, never per-lot, today.

### 6. Per-company configuration mechanism (relevant to "activable por empresa")

- `src/Ways.Application/Parametros/ServicioDeParametros.cs` + `src/Ways.Domain/Catalogos/ParametroConocido.cs`: a generic, open-ended key/value registry (`parametros` table: `clave`, `valor jsonb`, `id_empresa`, nullable `id_punto_venta`). Precedence: punto de venta > empresa > declared CLR default (ADR-13). Adding a new key is "an entry in `ParametroConocido`, not a migration" (doc-comment, line 12-13).
- Existing keys: `tolerancia_pago`, `vuelto_maximo`, `importe_adicional_recarga`, `slots_tickets_espera`, `zona_horaria` (stage 10, first string-typed key), `comision_porcentaje` (stage 10). `openspec/specs/parametros-operativos/spec.md` documents the resolution/fallback contract and the "no migration, no data statement" pattern used for stage 10's two new keys.
- **This is the natural mechanism for "módulo activable por empresa"**: a new boolean `ParametroConocido` (e.g. `lotes_habilitado`, `typeof(bool)`, default `false`) resolved at empresa level (an `id_punto_venta NULL` row) requires zero schema change and follows the exact pattern stage 10 already used for `zona_horaria`/`comision_porcentaje`. Caveat: `parametros` resolution today is called per-request inside services (`ServicioDeVentas` calls `ResolverParametroAsync` twice, pinned to a documented ≤16-round-trip budget) — adding a lote-enabled check to checkout's hot path needs to respect that budget discipline.

### 7. Articulo entity (relevant to "obligatorio/opcional/configurable por artículo")

- `src/Ways.Domain/Articulos/Articulo.cs`: no `control_de_lote`/`requiere_vencimiento` flag exists today. `EsProducto: bool` already gates whether an articulo touches stock at all (`false` = servicio, skips the entire stock loop in `ServicioDeVentas`/`ServicioDeCompras`). A per-articulo lot flag would be a new boolean column, same shape as `EsProducto`, and every stock-touching code path (sale, purchase, transfer, ajuste, conteo) would need to branch on it.
- Articulo is tenant-wide (no `id_empresa` column) — "activable por empresa" (parametros) and "control de lote por artículo" (a tenant-wide Articulo flag) are two DIFFERENT scoping levels that must reconcile: an articulo's lot-control flag would be visible/enforced only in empresas where the module parametro is on, but the flag itself lives at tenant scope. This is exactly the kind of interaction the proposal needs to resolve explicitly.

### 9. Multi-tenancy / RLS convention for new tables

- `docs/09-multi-tenancy.md:161-162`: app role has no `BYPASSRLS`; every request does `SET LOCAL app.tenant_id = @t`; every scoped table has policy `USING (id_tenant = current_setting('app.tenant_id')::int)`.
- Reference migration example: `src/Ways.Infrastructure/Persistencia/Migraciones/20260811033540_CostoCongeladoEnVentaEtapa9.cs` — adds nullable columns + two named CHECK constraints (`ck_{tabla}_{regla}` convention) to an existing tenant table, then does a one-shot idempotent backfill guarded by `SET LOCAL app.acceso = 'plataforma'` inside the migration's `Sql()` block (needed because `dotnet ef database update` doesn't run the tenant interceptor, and FORCE ROW LEVEL SECURITY would silently affect 0 rows otherwise). Backfill is idempotent via a `WHERE ... IS NULL` guard. **This is the exact pattern Stage 12 needs for "lote sin identificar" backfill of existing stock** when the module is activated for a tenant with pre-existing stock rows.
- `Stock`/`MovimientoStock` do NOT inherit `EntidadTenant` (hand-written `IdTenant` + manual RLS filter via `WaysDbContext.AplicarFiltroDeTenantEnStock`/`AplicarFiltroDeTenantEnMovimientoStock`, lines 516-546 of `WaysDbContext.cs`) — any new `lotes` table following the same "operativa" scoping (doc 09) as `stock` would need the same hand-rolled filter treatment if it's PK-only/no-audit, or can inherit `EntidadTenant` normally if it needs full audit columns.
- Composite FK convention observed throughout: `HasForeignKey(x => new { x.IdX, x.IdTenant }).HasPrincipalKey(p => new { p.Id, p.IdTenant })` with explicit named constraints (`fk_{tabla}_{referencia}`) and explicit named supporting indexes (`ix_{tabla}_{columnas}`) — EF's implicit PascalCase index names are always overridden.

## Constraints Any Design Must Respect

1. **Ledger append-only, non-negotiable**: no `movimientos_stock` row is ever updated or deleted. Any lot dimension must be additive columns/rows, never a retrofit that requires editing history.
2. **Sum invariant**: `stock.cantidad` (aggregate cache) must keep equalling `SUM(movimientos_stock.cantidad)` per `(id_articulo, id_punto_venta)` regardless of how many motivos or lot rows exist — this is spec-asserted and test-covered today.
3. **Ascending-`id_articulo` lock order** in checkout and purchase confirm, and the **ascending 2N-key order** in transfers, are deadlock-prevention devices, not style choices — extending the unit of locking to include `id_lote` requires extending these orders consistently across THREE independent call sites (`ServicioDeVentas`, `ServicioDeCompras`, `ServicioDeStock`) that do not share a helper.
4. **Row-lock-as-serialization via `INSERT ... ON CONFLICT ... RETURNING`** is the only concurrency primitive used for stock (design decision 1, "no advisory locks needed"). A per-lot balance table would need the same shape (PK on `(id_articulo, id_punto_venta, id_lote)` or similar) to keep this guarantee.
5. **Decide-then-commit split** in `ServicioDeVentas.EmitirAsync`: all decision-making (FEFO lot selection would live here) must happen BEFORE the transaction opens, as pure reads + rules, producing an immutable plan; nothing decision-relevant may run inside the retryable transaction lambda.
6. **RLS is FORCE-enabled, app role has no BYPASSRLS in production** — any migration backfill (e.g., "lote sin identificar" seeding) must use `SET LOCAL app.acceso = 'plataforma'` inside the migration's raw SQL, exactly as `CostoCongeladoEnVentaEtapa9` does.
7. **Snapshot immutability of comprobante items** — `ItemComprobanteVenta`/`ItemComprobanteCompra` are frozen at emission time; if a lot reference is added to either, it becomes part of that permanent snapshot, never re-derived later.
8. **Comprobantes are the only two write choke points for their respective motivos** — `ServicioDeCompras` explicitly forbids being merged into `ServicioDeStock` (Slice 2 non-negotiable per its own doc-comment); expect the same siloing pressure for Stage 12's new writers.
9. **`parametros` resolution round-trip budget**: `ServicioDeVentas.EmitirAsync` is pinned to a documented ≤16 round-trips; any lote-enabled check added to the sale hot path must be justified within that budget or resolved via a cheaper mechanism (e.g., caching the flag on the request context rather than a fresh `ServicioDeParametros` call per checkout).

## Evidence Per Open Decision (no decisions made here — proposal's job)

**Lote obligatorio/opcional/configurable por artículo:**
- `Articulo.EsProducto` is the closest existing precedent for a per-articulo stock-behavior flag, but it's binary and simple (skip stock entirely vs. not). A three-way obligatorio/opcional/no-aplica semantic has no existing precedent in the codebase — would be new domain logic.
- `Articulo` is tenant-wide, not empresa-scoped, while the module toggle (via `parametros`) is empresa-scoped — the proposal must resolve what an "opcional" flag means in an empresa where the module is off.

**Stock existente al activar (lote "sin identificar"):**
- The `CostoCongeladoEnVentaEtapa9` migration is the direct precedent for a backfill-on-activation shape: idempotent, `SET LOCAL app.acceso = 'plataforma'`, `WHERE ... IS NULL` guard. But that backfill ran unconditionally for all tenants at deploy time — Stage 12's backfill would need to be per-tenant/per-empresa (only when the module is turned on), which is a NEW pattern (activation-time backfill, not deploy-time backfill). No existing per-tenant on-demand migration precedent exists in this codebase.

**FEFO sugerencia vs imposición:**
- `ServicioDeVentas.EmitirAsync`'s decide-then-commit split is exactly where a FEFO suggestion/selection algorithm would run (pure read+rule phase, before the transaction). Nothing in the current sale flow validates or constrains WHICH unit is decremented — `UpsertStockAsync` is a pure aggregate delta with no unit-level identity — so today's design has zero enforcement mechanism for "must sell oldest first"; imposing FEFO would require either (a) a lot-scoped balance table with its own row lock per lot, selected by the pre-transaction planning phase, or (b) staying a suggestion only, enforced nowhere server-side (matches `PrecioSugerido` precedent in `ItemComprobanteCompra` — "a suggestion, never auto-applied", design decision 3 of comprobantes-compra spec).

**Interacción con transferencias:**
- Transfers have NO header/state entity and NO in-transit state (spec: "the transfer completes or it does not happen at all") — a lot-aware transfer must decide at submission time exactly which lot(s) move, atomically, in the same all-or-nothing shape. The existing 2N-key ascending lock order would need to become a `3N`-or-more-key order if `id_lote` is part of the transfer unit.
- The existing back-office tightening (refuse if origin goes negative) is per-articulo aggregate today — would need to become per-lot if lot balances are tracked independently, which changes the refusal semantics (an aggregate could be sufficient while a specific lot's balance underflows).

**Relación con notas de crédito:**
- NCX devoluciones flow through the exact same `EjecutarTransaccionAsync` code path as sales (same ascending-`id_articulo` stock loop, sign-flipped via `ItemComprobanteVenta.Cantidad`). There is no dedicated devolución entity and no mandatory link to the original sale (`id_comprobante_asociado` is optional). This means: unless a lot reference is added to `ItemComprobanteVenta` (populated at original sale time) AND NCX emission is made to look it up, there is no way today to know which lot a returned unit re-enters — the NCX line would need either an explicit client-supplied `id_lote` or a mandatory link back to the original sale's item-level lot.
- By contrast, anulación (as opposed to NCX/devolución) DOES iterate the original comprobante's own items, so if a lot were stored on `ItemComprobanteVenta`, anulación's reversal would trivially know the correct lot — this is a materially easier path than NCX devoluciones.

**Relación con `movimientos_stock` (ledger sin dimensión de lote hoy):**
- Adding `id_lote` to `movimientos_stock` is additive (nullable initially, or NOT NULL only for lot-controlled articulos) and doesn't break the append-only/sum-invariant constraints IF the aggregate `stock.cantidad` cache stays keyed by `(id_articulo, id_punto_venta)` only (lot becomes an additional dimension queried from the ledger or a new per-lot cache table, not a replacement of the existing cache).
- The three independent raw-SQL writer call sites (`ServicioDeVentas`, `ServicioDeCompras`, `ServicioDeStock`) all need coordinated changes — there is no shared helper to modify once.

## Risks / Unknowns

- **No push-alert mechanism exists at all** — "alertas de mercadería próxima a vencer" (doc 11 wording) cannot mean a push/email notification without net-new infrastructure (email sender, background job scheduler) that this codebase has never built; likely needs to be scoped down to a pull-model dashboard/report tile using the existing `TablaExportable`/reportes pattern, or the proposal must explicitly add notification infra as new scope.
- **Three independent write sites with no shared helper** is the single biggest implementation-size risk doc 11 already flags ("tamaño: grande") — every lot-aware change to the stock-writing contract (signature of `InsertarMovimientoStockAsync`/`UpsertStockAsync`, or a new lot-balance table) must be replicated three times, correctly, under three different lock-order disciplines (ascending `id_articulo`; ascending `id_articulo` again for compras; ascending 2N-tuple for transfers).
- **NCX devolución lot traceability gap** — today's `ItemComprobanteVenta` has zero link to which unit/lot was sold, and NCX doesn't require referencing the original sale at all. Any FEFO/lot design that assumes "we know which lot to restock on a return" is not backed by current data; this needs explicit product/design resolution (mandatory `id_comprobante_asociado` for lot-controlled articulos? client picks lot manually on NCX?).
- **Per-articulo vs per-empresa scoping mismatch** — `Articulo` is tenant-wide, `parametros` (the natural module-toggle mechanism) is empresa/PV-scoped. An articulo's lot-control flag and the module's empresa-level activation are two different axes that the proposal must reconcile (e.g., can an articulo be lot-controlled in one empresa of the tenant but not another, given articles are shared tenant-wide by default via `DisponibleParaTodas`?).
- **Activation-time backfill is a new migration pattern** — existing backfills (e.g., `CostoCongeladoEnVentaEtapa9`) run once at deploy for ALL tenants; Stage 12 needs a DIFFERENT trigger (per-tenant, on-demand when the module is switched on), which likely means an application-level backfill operation (a new admin-triggered endpoint/job), not a plain EF migration — this is new architectural surface, not a reuse of the existing pattern.
- **Conteo de inventario is explicitly scoped to per-articulo, never per-lot** today, and its own spec states "out of scope: any full-count snapshot/freeze/variance workflow" — a lot-aware conteo (counting each lot separately) is a materially bigger feature than the current single-total-per-articulo conteo.

## Ready for Proposal

Yes. The current-state map, constraints, and evidence above give the proposal phase everything it needs to resolve the five open decisions (lote obligatorio/opcional/configurable; stock inicial al activar; FEFO sugerencia vs imposición; interacción con transferencias/NC; relación con movimientos_stock) without further code investigation. The one thing flagged upward: "alertas" as worded in doc 11 has no push-notification precedent anywhere in the codebase — the proposal should explicitly scope this to a pull/report surface unless new notification infrastructure is accepted as in-scope.
