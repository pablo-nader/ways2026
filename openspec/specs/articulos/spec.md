# Articulos Specification

## Purpose

Defines the `articulos` table (doc 10 §3): tenant-wide entity (no
`id_empresa` ownership), full field set, the availability model
(`disponible_para_todas` + `articulos_empresas`), the mandatory autogenerated
`codigo_interno`, and artículo ABM.

## Requirements

### Requirement: Articulo Schema At Rest

`articulos` MUST be tenant-wide (`id_tenant`, no `id_empresa` column, doc 10
§3) with: `nombre`, `descripcion NULL`, `id_area NOT NULL`, `id_categoria
NULL`, `id_marca NULL`, `id_grupo NULL`, `id_proveedor_habitual NULL`,
`id_alicuota_iva NOT NULL`, `unidad_venta` (`unidad`|`peso`),
`unidades_por_bulto NULL`, `es_producto`, `costo_lista NULL`,
`descuento_proveedor NULL`, `costo_nominal NULL`, `disponible_para_todas
BOOLEAN NOT NULL DEFAULT true`, `activo`.

#### Scenario: Create articulo with only required fields

- GIVEN a tenant admin submits `nombre`, `id_area`, `id_alicuota_iva`,
  `unidad_venta`, `es_producto`
- WHEN the row is persisted
- THEN it succeeds with all optional fields NULL and `disponible_para_todas
  = true`

#### Scenario: Invalid clasificador or alicuota reference maps to 400

- GIVEN a create request references a non-existent `id_area`, `id_categoria`,
  `id_marca`, `id_grupo`, or `id_alicuota_iva`
- WHEN the insert reaches Postgres
- THEN 23503 is raised and `ManejadorDeErrores` maps it to 400
  `referencia_invalida`

### Requirement: codigo_interno Mandatory And Autogenerated

Every artículo MUST have a `codigo_interno`, unique per tenant (partial index
`WHERE deleted_at IS NULL`). When omitted at creation, the system MUST
autogenerate it from an atomic per-tenant counter (same family as
`clientes.numero`); a user-supplied value MUST be accepted when it does not
collide with an existing one for the tenant. This supersedes doc 10's
`NULL`-able marking of the column.

#### Scenario: Omitted codigo_interno is autogenerated

- GIVEN a tenant admin creates an artículo without `codigo_interno`
- WHEN the row is persisted
- THEN a value is assigned from the tenant's atomic counter

#### Scenario: User-supplied codigo_interno is honored when unique

- GIVEN a tenant admin creates an artículo with an explicit unused
  `codigo_interno`
- WHEN the row is persisted
- THEN it succeeds with the supplied value, unchanged

#### Scenario: Duplicate user-supplied codigo_interno is rejected

- GIVEN tenant 1 already has an artículo with `codigo_interno = "1001"`
- WHEN tenant 1 creates another artículo with the same value
- THEN the request is rejected with 409 mapped from Postgres 23505

#### Scenario: Concurrent autogeneration yields no gaps or duplicates

- GIVEN two concurrent create requests for tenant 1, both omitting
  `codigo_interno`
- WHEN both transactions commit
- THEN each receives a distinct autogenerated value and both succeed with 201

### Requirement: Availability Model (disponible_para_todas)

`disponible_para_todas = true` (default) MUST make the artículo visible to
every empresa of the tenant, including empresas created after the artículo —
automatically, with no `articulos_empresas` backfill required. `false` MUST
restrict visibility to the empresas explicitly listed in `articulos_empresas`.

#### Scenario: Default-true articulo is visible to a later empresa

- GIVEN an artículo with `disponible_para_todas = true` created before
  empresa B exists
- WHEN empresa B is provisioned for the same tenant and the artículo is
  queried for empresa B
- THEN the artículo is visible without any new `articulos_empresas` row

#### Scenario: Explicit subset excludes other empresas

- GIVEN an artículo with `disponible_para_todas = false` and one
  `articulos_empresas` row for empresa A
- WHEN the artículo is queried for empresa B (same tenant)
- THEN the artículo is not visible

#### Scenario: Restricting availability requires at least one subset row

- GIVEN an artículo currently `disponible_para_todas = true`
- WHEN a tenant admin sets it to `false` without providing any
  `articulos_empresas` row
- THEN the request is rejected by a service-level guard before reaching the
  database

### Requirement: articulos_empresas Junction Schema

`articulos_empresas` MUST hold rows only when its artículo has
`disponible_para_todas = false`, with `PRIMARY KEY (id_articulo, id_empresa)`
and composite FKs to `articulos` and `empresas` that enforce both belong to
the same `id_tenant`.

#### Scenario: Cross-tenant empresa reference is blocked

- GIVEN tenant 1's artículo and tenant 2's empresa
- WHEN a tenant 1 admin attempts to add tenant 2's empresa to the artículo's
  subset
- THEN the request is rejected with 400 `referencia_invalida` via a
  tenant-scoped existence pre-check (not `IgnoreQueryFilters`)

### Requirement: Articulo ABM Lifecycle and Authorization

Artículos MUST support list/create/edit/soft-delete, gated by
`GestionDeCatalogo` (tenant `admin` only — `root` and `vendedor` excluded).

#### Scenario: Admin creates and soft-deletes an articulo

- GIVEN a tenant admin
- WHEN they create an artículo and later soft-delete it
- THEN it is persisted under the admin's `id_tenant`, and after deletion
  `deleted_at` is set and it no longer appears in the default list

#### Scenario: Vendedor blocked from writing

- GIVEN a user with the `vendedor` role
- WHEN they call the artículo create endpoint
- THEN the request is rejected with an authorization error

### Requirement: Tenant Isolation for Articulos And articulos_empresas

`articulos`, `articulos_empresas`, and the `codigo_interno` counter MUST
enforce the two-layer isolation guarantee (EF Core global query filter +
Postgres RLS without `BYPASSRLS`) established in stage 1.

#### Scenario: EF filter blocks cross-tenant read

- GIVEN a request scoped to tenant 1
- WHEN a query executes through the normal `DbContext` for an artículo of
  tenant 2
- THEN no rows are returned

#### Scenario: RLS blocks a read that bypasses EF

- GIVEN the app DB role has no `BYPASSRLS`
- WHEN a raw SQL query or `IgnoreQueryFilters()` reads tenant 2's `articulos`
  or `articulos_empresas` while `app.tenant_id = 1`
- THEN RLS returns zero rows
