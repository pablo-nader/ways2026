# 09 — Multi-tenancy: tenants, empresas y puntos de venta

> El sistema se va a vender a terceros. Este documento fija el modelo de tenancy **antes**
> de que exista el resto del schema, porque es la única decisión que no se puede
> retro-encajar: cada tabla que se cree de acá en adelante nace scopeada.

## Jerarquía

```
tenant  (el cliente que paga: "Supermercados Pérez SRL")
  └── empresa  (razón social / CUIT: puede tener varias)
        └── punto_venta  (el local físico o virtual)
```

- Un **tenant** es la unidad comercial y de aislamiento: quién contrata, quién paga,
  cuyos datos jamás se mezclan con los de otro tenant.
- Una **empresa** es la unidad fiscal: razón social, CUIT, condición frente al IVA.
  Un tenant puede operar con varias razones sociales.
- Un **punto de venta** es la unidad operativa: donde se abren turnos de caja, se emiten
  comprobantes y se cuenta stock. Coincide con el concepto de punto de venta de AFIP/ARCA
  (el prefijo `NNNN` del número de comprobante `NNNN-NNNNNNNN`).

El negocio actual (Ways/Alsina) es el tenant 1: una empresa, dos puntos de venta.

## Decisión: una base compartida, no una base por tenant

| | Base compartida (`tenant_id` por fila) | Base por tenant |
|---|---|---|
| Migraciones de schema | una sola vez | N veces, con orquestación |
| Backup / restore | uno global; por tenant vía export lógico | trivial por tenant |
| Provisioning de un tenant nuevo | `INSERT INTO tenants` | crear base + migrar + configurar |
| Aislamiento | lógico (query filters + RLS) | físico |
| Costo de infraestructura | una instancia | crece con cada tenant |
| Consultas cross-tenant (métricas del negocio) | directas | imposibles sin ETL |
| Riesgo principal | un bug de filtro filtra datos ajenos | deriva de versiones entre bases |

**Decisión: base compartida.** El equipo es una persona, los tenants son comercios chicos
(miles de artículos, cientos de miles de ventas en años) y la operatoria es EasyPanel con
una instancia de Postgres. El riesgo del modelo compartido —un filtro mal aplicado— se
mitiga con dos capas independientes (ver "Aislamiento").

**Cláusula de escape:** el `tenant_id` en cada fila hace posible extraer un tenant a su
propia base el día que un cliente lo exija (export lógico filtrado por `tenant_id`).
La inversa —consolidar N bases en una— exigiría renumerar todos los IDs.

## Tablas de organización

```sql
tenants (
    id_tenant   integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    nombre      citext NOT NULL,
    estado      estado_tenant NOT NULL DEFAULT 'activo',   -- activo | suspendido | baja
    -- created_at / updated_at / deleted_at según EntidadBase
);

empresas (
    id_empresa    integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_tenant     integer NOT NULL REFERENCES tenants,
    razon_social  citext NOT NULL,
    nombre_fantasia citext NULL,
    cuit          varchar(13) NULL,
    id_condicion_fiscal integer NULL REFERENCES condiciones_fiscales,  -- Etapa 19a, FK simple
    UNIQUE (id_empresa, id_tenant)          -- habilita FKs compuestas (ver Aislamiento)
);

puntos_venta (
    id_punto_venta integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_tenant      integer NOT NULL REFERENCES tenants,
    id_empresa     integer NOT NULL,
    nombre         citext NOT NULL,
    domicilio, horario, whatsapp, instagram, facebook, web, ...,   -- lo que ya define el doc 03
    numero_fiscal  integer NULL,             -- Etapa 19a: PtoVta ARCA, UNIQUE por empresa (1..99999)
    FOREIGN KEY (id_empresa, id_tenant) REFERENCES empresas (id_empresa, id_tenant),
    UNIQUE (id_punto_venta, id_tenant)
);
```

>
> Esta etapa también agrega `certificados_fiscales`, una **DESVIACIÓN DOCUMENTADA** de la forma
> de catálogo de esta sección: mientras un catálogo de tenant lleva `id_empresa NULL` = *"vale
> para todas las empresas del tenant"* (ver la regla de scoping más abajo), `certificados_fiscales`
> lleva **`id_empresa NOT NULL`** — un certificado X.509 pertenece a UN CUIT (una empresa) y
> nunca se comparte entre empresas del mismo tenant, misma forma exacta que `puntos_venta`
> (scoping operativa: `id_tenant` + `id_empresa`/`id_punto_venta` no-nulos). `numeraciones_fiscales`
> es scoping **operativa** estándar (`id_tenant` + `id_punto_venta`), sin desvío — mismo criterio
> que `numeraciones_comprobante`.

## Regla de scoping por tipo de tabla

Toda tabla del sistema cae en una de estas tres categorías. Al crear una tabla nueva,
lo primero es decidir en cuál está:

| Categoría | Scope | Tablas |
|---|---|---|
| **Catálogo** | `id_tenant` + `id_empresa NULL` | `proveedores`, `clientes`, `marcas`, `grupos`, `areas`, `listas_precio`, `ofertas` |
| **Tenant-wide (disponibilidad por empresa)** | `id_tenant`, SIN `id_empresa` | `articulos`, `codigos_barra`, `precios` |
| **Operativa** | `id_tenant` + `id_punto_venta` | `ventas`, `items_venta`, `gastos`, `stock`, `movimientos_stock`, `turnos_caja`, `movimientos_tesoreria`, `arqueos_recargas`, `numeraciones_comprobante` |
| **Global** | sin tenant | `roles`, `permisos`, planes/facturación del SaaS |

La categoría **Tenant-wide** resuelve la misma pregunta de negocio ("¿comparten empresas
un mismo artículo?") con un modelo distinto al de `id_empresa NULL`: en vez de una columna
nullable en la fila del artículo, `disponible_para_todas` (default `true`) más una tabla
puente `articulos_empresas` acotan el subconjunto de empresas cuando hace falta — sin
backfill al crear una empresa nueva, porque la ausencia de fila en la puente ya significa
"disponible". `precios` sigue al artículo: es `id_tenant` sin `id_empresa`, igual que
`articulos`. Detalle completo del modelo en doc 10 §3.

### Catálogo: compartir o no compartir entre empresas

La regla pedida es: *"las empresas podrían o no compartir proveedores, clientes,
artículos y demás"*. Se resuelve con una sola columna:

```sql
-- en toda tabla de catálogo
id_tenant  integer NOT NULL,
id_empresa integer NULL,     -- NULL  = compartido por todas las empresas del tenant
                             -- valor = privado de esa empresa
```

- La consulta estándar de una empresa es
  `WHERE id_tenant = @t AND (id_empresa IS NULL OR id_empresa = @e)`.
- El caso típico (tenant de una sola empresa) funciona sin pensar en nada: todo `NULL`.
- Un artículo compartido y uno privado pueden convivir; ante código de barras duplicado,
  gana el privado (misma lógica que un override).

**Límite conocido y aceptado:** compartido significa *con todas* las empresas del tenant.
Compartir entre un subconjunto (la empresa A y B comparten artículos, la C no) exigiría
una entidad "ámbito de catálogo" intermedia. No se implementa hoy; si algún día hace
falta, `id_empresa NULL` se reinterpreta como "ámbito default" sin romper datos.

### Operativa: siempre por punto de venta

Ventas, gastos, turnos, stock y movimientos nacen en un punto de venta y no se comparten
jamás. Ya era la regla 10 del legacy ("toda operación scopeada por `id_punto_venta`") y
el doc 03 ya define `stock` por `(articulo_id, punto_venta_id)`.

### Numeración de comprobantes: por punto de venta, atómica

Los puntos de venta comparten todo lo de su empresa **salvo la numeración**:

```sql
numeraciones_comprobante (
    id_tenant         integer NOT NULL,
    id_punto_venta    integer NOT NULL,
    tipo_comprobante  varchar(30) NOT NULL,   -- ticket, retiro, cierre_caja, ...
    proximo_numero    bigint NOT NULL DEFAULT 1,
    PRIMARY KEY (id_punto_venta, tipo_comprobante)
);
```

La emisión toma el número con
`UPDATE ... SET proximo_numero = proximo_numero + 1 ... RETURNING proximo_numero - 1`
dentro de la transacción de la venta: sin huecos, sin duplicados bajo concurrencia.
El número visible sigue siendo `NNNN - NNNNNNNN` (punto de venta + correlativo),
igual que el legacy y alineado con el modelo de AFIP/ARCA para el día que llegue la
facturación electrónica.

## Aislamiento: dos capas independientes

**Capa 1 — EF Core.** Un `ITenantActual` (scoped por request, resuelto desde la sesión)
y un query filter global aplicado por convención a toda entidad con `IdTenant`, igual que
hoy se aplica el filtro de `deleted_at` desde `EntidadBase`:

```csharp
builder.HasQueryFilter(e => e.IdTenant == tenantActual.Id && e.DeletedAt == null);
```

Los `INSERT` estampan `IdTenant` automáticamente en `SaveChanges`; nunca lo setea el
código de un caso de uso.

**Capa 2 — Row Level Security de Postgres.** La aplicación se conecta con un rol sin
`BYPASSRLS`; cada request setea `SET LOCAL app.tenant_id = @t` y cada tabla scopeada
tiene una policy `USING (id_tenant = current_setting('app.tenant_id')::int)`.

La capa 2 existe para que un `IgnoreQueryFilters()` mal puesto, un SQL crudo o un bug
del ORM **no puedan** cruzar datos de tenants. El filtro de EF es performance y
ergonomía; RLS es la garantía.

**FKs compuestas.** Las claves foráneas entre tablas scopeadas incluyen `id_tenant`
(`FOREIGN KEY (id_x, id_tenant) REFERENCES x (id_x, id_tenant)`). Una fila del tenant 1
no puede referenciar un artículo del tenant 2 ni por bug.

## Usuarios y roles en el mundo multi-tenant

Impacto sobre el doc 08 (ya implementado):

- `usuarios` gana `id_tenant NULL`: `NULL` = staff de la plataforma (quien vende el
  sistema), valor = usuario del tenant.
- El rol `root` pasa a ser rol de plataforma: administra tenants, no opera ninguno.
- `admin` pasa a ser el administrador **del tenant**: gestiona sus usuarios, empresas,
  puntos de venta y catálogo. `PoliticaDeRoles` incorpora la regla "un admin solo ve y
  gestiona usuarios de su propio tenant".
- `asignaciones_empleado` (doc 03) sigue siendo la relación usuario ↔ rol ↔ punto de
  venta; la selección de punto de venta del legacy (A2) se conserva, ahora filtrada
  además por tenant.
- La sesión guarda `tenant_id` resuelto en el login; jamás viaja como parámetro editable
  por el cliente.

## Baja lógica de la organización (Etapa 20 — stage-20-organizacion-relaciones-y-bajas)

La jerarquía tenant → empresa → punto de venta ya se podía crear (aprovisionamiento, ADR-16)
y editar; desde esta etapa también se puede **dar de baja**, con una única semántica:

- **La baja es SIEMPRE lógica, nunca física.** Se sella `deleted_at` (y, para un tenant,
  además `EstadoTenant.Baja`); ninguna fila se borra de la base. Todas las FK del modelo son
  `DeleteBehavior.Restrict`, así que no hay ni un `DELETE FROM` sobre `tenants`, `empresas`,
  `puntos_venta` ni `usuarios`. Recuperar una baja hecha por error es un `UPDATE` de una
  columna.
- **El discriminador "prístino" es una comparación estricta contra el `CreatedAt` de la propia
  entidad.** Lo que el aprovisionamiento sembró en el mismo instante que la entidad no cuenta
  como uso; cuenta lo que el cliente creó DESPUÉS de esa marca. Un dependiente que el cliente
  creó y después dio de baja **sigue bloqueando**: la baja de una fila no borra que hubo
  operación.
- **El conjunto de dependientes se descubre de la metadata de EF, nunca de una lista a mano.**
  Cada tipo que referencia a la entidad cae en exactamente uno de tres buckets (directo,
  puenteado, ignorado) o el build falla, y hay un inventario ordenado versionado como golden:
  una tabla nueva que nadie clasifique rompe un test, no la producción. Hay exactamente **dos
  carve-outs**, cada uno con su motivo escrito y su propio test.
- **Una fila de catálogo compartido (dueño `NULL`) no bloquea**, en coherencia con la regla de
  `id_empresa NULL` de este documento.
- **La cascada está acotada a la proyección de organización y comparte un solo instante.** Dar
  de baja un tenant da de baja, con el mismo timestamp y dentro de la misma transacción, sus
  empresas, sus puntos de venta y sus usuarios; dar de baja una empresa arrastra sus puntos de
  venta. La cascada no toca datos operativos (ventas, stock, caja): esos son justamente los que
  BLOQUEAN la baja.
- **Los mínimos estructurales se chequean ANTES del guard de uso**, con códigos propios: un
  tenant no puede quedarse sin ninguna empresa viva, y una empresa no puede quedarse sin
  ningún punto de venta vivo. Los hermanos ya dados de baja no cuentan como vivos.
- **El set completo de rechazos es de seis códigos**: `tenant_en_uso`, `empresa_en_uso`,
  `punto_venta_en_uso`, `usuario_en_uso`, `ultima_empresa_del_tenant` y
  `ultimo_punto_venta_de_la_empresa`. Los seis viajan como `409` con su `codigo` exacto; la web
  elige su copia por el **código**, nunca por el mensaje.
- **La baja nunca se convierte en un oráculo de existencia entre tenants.** Un admin que apunta
  a una entidad de otro tenant recibe `404`, idéntico al de un id inexistente — nunca `403` ni
  un `409` que delate el estado de la fila. Es la misma conducta deliberada de
  `PoliticaDeRoles.ValidarAlcanceDeTenant` (ADR-8), y la web la respeta en su copia.
- **Autorización sin policies nuevas**: cada `DELETE` reusa la policy del grupo de rutas al que
  ya pertenece — `SoloPlataforma` para tenants, `GestionDeOrganizacion` para empresas y puntos
  de venta. `Politicas.cs` no se tocó.
- Un admin de un tenant dado de baja **no puede iniciar sesión**: la búsqueda del login corre
  bajo el query filter de baja lógica, así que la cuenta simplemente no existe y la respuesta es
  `401 credenciales_invalidas` (no `403 tenant_suspendido`, que sigue siendo la respuesta del
  tenant **suspendido**).

**Latencia registrada.** Ways no expone hoy ninguna ruta que cree una *segunda* empresa o un
*segundo* punto de venta, así que a través de la API el mínimo estructural dispara siempre y
`empresa_en_uso` / `punto_venta_en_uso` solo son alcanzables por debajo de la capa HTTP. La baja
de empresa y de punto de venta ships **latente**: correcta y probada, y utilizable en cuanto
exista un alta que permita un segundo hermano.

**Cero DDL.** Esta etapa no crea, altera ni borra ninguna tabla ni columna: `deleted_at` y
`estado` ya existían desde la etapa 1.
