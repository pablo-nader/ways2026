# 08 — Usuarios, roles y login

Primera tabla del sistema nuevo. No es una migración del `usuarios` viejo: es una tabla
nueva que cubre **solo acceso**. Los clientes de cuenta corriente van a su propia tabla
cuando toque migrarlos.

## Esquema

### `roles`

```sql
CREATE TABLE roles (
    id_rol      integer PRIMARY KEY,          -- fijo, no identity
    nombre      citext       NOT NULL,
    descripcion varchar(255) NULL,
    created_at  timestamptz  NOT NULL,
    updated_at  timestamptz  NOT NULL,
    deleted_at  timestamptz  NULL
);
CREATE UNIQUE INDEX ux_roles_nombre ON roles (nombre) WHERE deleted_at IS NULL;
```

| `id_rol` | Nombre | Alcance |
|---|---|---|
| `1` | `root` | Todo. No se crea ni se elimina desde la aplicación |
| `2` | `admin` | Gestiona usuarios (salvo root y otros admin), catálogo, configuración |
| `3` | `supervisor` | Todavía sin permisos propios |
| `4` | `vendedor` | Todavía sin permisos propios |

El ID es fijo y conocido por el código (`RolConocido`), por eso la tabla **no** usa identity:
se siembra con IDs explícitos.

### `usuarios`

> Esquema al día con la migración `UsuariosMultiTenant` (multi-tenancy, doc 09). El detalle
> completo de la decisión — por qué `id_tenant` es nullable, por qué el unique de `usuario`
> pasa a ser compuesto — vive en
> `openspec/changes/stage-1-organization-and-catalogs/specs/usuarios-tenant-scoping/spec.md`;
> acá queda el esquema resultante.

```sql
CREATE TYPE estado_usuario AS ENUM ('activo', 'bloqueado', 'inactivo');

CREATE TABLE usuarios (
    id_usuario              integer GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    id_tenant               integer        NULL REFERENCES tenants(id_tenant),
    usuario                 citext         NOT NULL,
    mail                    citext         NOT NULL,
    id_rol                  integer        NOT NULL REFERENCES roles(id_rol),
    estado                  estado_usuario NOT NULL DEFAULT 'activo',
    password_hash           varchar(255)   NOT NULL,
    password_algoritmo      varchar(30)    NOT NULL,
    password_actualizado_el timestamptz    NOT NULL,
    ultima_conexion         timestamptz    NULL,
    ultimo_intento_fallido  timestamptz    NULL,
    intentos_fallidos       smallint       NOT NULL DEFAULT 0,
    created_at              timestamptz    NOT NULL,
    updated_at              timestamptz    NOT NULL,
    deleted_at              timestamptz    NULL
);
-- NULLS NOT DISTINCT: dos cuentas de plataforma (id_tenant NULL) con el mismo `usuario`
-- chocan igual que dos cuentas del mismo tenant — la agrupación de plataforma cuenta como
-- "un tenant más" a este efecto (ADR-7, usuarios-tenant-scoping/spec.md).
CREATE UNIQUE INDEX ux_usuarios_usuario ON usuarios (id_tenant, usuario)
    NULLS NOT DISTINCT WHERE deleted_at IS NULL;
-- `mail` sigue siendo único GLOBAL, no por tenant: dos tenants no pueden compartir cuenta.
CREATE UNIQUE INDEX ux_usuarios_mail    ON usuarios (mail)    WHERE deleted_at IS NULL;
CREATE INDEX        ix_usuarios_rol     ON usuarios (id_rol);
CREATE INDEX        ix_usuarios_tenant  ON usuarios (id_tenant);
```

RLS (doc 09, ADR-4/ADR-5/ADR-15) aísla `usuarios` por tenant igual que el resto de las tablas
scopeadas, más dos policies propias para la ventana de login: antes de que exista una sesión,
`POST /api/auth/login` necesita poder leer y actualizar cualquier cuenta por `mail`, de
cualquier tenant, porque todavía no hay un tenant resuelto contra el cual filtrar.

## Decisiones y por qué

### `estado` es un enum nativo de PostgreSQL

No un `smallint`. El problema concreto del legacy era `tipoUser=2`, `tipo=95`, `lista=2`:
números mágicos que hacen ilegible cualquier consulta a mano y obligan a ir al código para
entender un `SELECT`. Con un enum, `WHERE estado = 'bloqueado'` se lee solo.

Agregar un valor es `ALTER TYPE estado_usuario ADD VALUE 'suspendido'`. Quitarlo es caro,
así que conviene pensar los valores antes de sumarlos.

Por JSON viaja como texto (`"Activo"`), nunca como el ordinal.

### No hay columna de salt

El `password_hash` es un string autodescriptivo que ya contiene el formato, el algoritmo,
la cantidad de iteraciones **y el salt**. Guardar el salt aparte era necesario cuando se
usaba MD5 o SHA1 pelado; con un hasher moderno duplica el dato y obliga a versionar dos
columnas en lugar de una.

Hoy: **PBKDF2-SHA512, 100.000 iteraciones, salt aleatorio de 128 bits**, vía el
`PasswordHasher` de ASP.NET Core.

`password_algoritmo` guarda el identificador (`pbkdf2-sha512-v3`) para poder migrar después.
El día que se pase a Argon2id, se implementa otro `IHasheadorDeContrasenas` y las cuentas
se rehashean solas: al iniciar sesión, un hash viejo devuelve `ValidaPeroHayQueRehashear`
y se reescribe en el momento. Nadie tiene que resetear su contraseña.

### Los unique son parciales

`WHERE deleted_at IS NULL`. Con un unique común, dar de baja a "vendedor1" dejaría el alias
quemado para siempre: para reusarlo habría que borrar la fila físicamente, que es justo lo
que el soft delete quiere evitar.

### `citext` en `usuario` y `mail`

La comparación es case-insensitive en el motor. `Root` y `root` son el mismo usuario, y
`A1@T.com` colisiona con `a1@t.com`. Sin `citext` haría falta indexar sobre `lower(columna)`
y acordarse de usar `lower()` en cada consulta.

### `created_at` / `updated_at` / `deleted_at` en todas las tablas

Convención del proyecto, definida en `EntidadBase`. El filtro de baja lógica se aplica
automáticamente a toda entidad que herede de ahí; para ver las bajas hay que pedir
`IgnoreQueryFilters()` explícitamente.

## Reglas de autorización

En [`PoliticaDeRoles`](../src/Ways.Domain/Usuarios/PoliticaDeRoles.cs) — dominio puro,
testeable sin base:

| Regla |
|---|
| Solo `root` y `admin` acceden al ABM de usuarios |
| **Nadie** puede crear ni asignar el rol `root` |
| Solo `root` puede crear o asignar el rol `admin` |
| Un `admin` no puede editar ni dar de baja una cuenta `root` |
| Las cuentas `root` no se eliminan |
| Nadie puede eliminarse a sí mismo |
| Cualquiera puede cambiar su propia contraseña |

Cambiar el rol se valida aparte de editar los datos: podés corregirle el mail a un
supervisor sin tener permiso para convertirlo en admin.

## Login

- `POST /api/auth/login` con `{ mail, password }`. Es por `mail`, no por `usuario` (etapa 1
  de multi-tenancy, doc 09): el `mail` es único global y resuelve la cuenta —y con ella el
  tenant— sin que el request tenga que cargar ningún contexto de tenant de antemano. El
  detalle del contrato de login vive en
  `openspec/changes/stage-1-organization-and-catalogs/specs/usuarios-y-login/spec.md`.
- El mensaje de error es **el mismo** para mail inexistente y contraseña incorrecta.
  El legacy los distinguía (*"El usuario ingresado es incorrecto"* vs *"La contraseña
  ingresada es incorrecta"*), lo que permite enumerar cuentas. Además, ante un mail
  inexistente se verifica igual contra un hash descartable para que el tiempo de respuesta
  no delate si la cuenta existe.
- El estado de la cuenta (bloqueada / inactiva) recién se informa **después** de validar
  la contraseña. Si no, sería otra vía de enumeración.
- **5 intentos fallidos** dejan la cuenta en `bloqueado`. Un root o admin la desbloquea
  desde el ABM, lo que también reinicia el contador.
- Un ingreso exitoso limpia los intentos fallidos y actualiza `ultima_conexion`.

### Sesión

- Cookie `ways.sesion`: `HttpOnly`, `SameSite=Lax`, `Secure` cuando la conexión original
  es HTTPS. El token nunca pasa por JavaScript.
- **Expiración deslizante de 1 hora.** Cada request dentro de la ventana la renueva;
  una hora de inactividad la vence.
- Persistente: sobrevive al cierre del navegador.
- En cada request se revalida que la cuenta siga activa. Bloquear o dar de baja a alguien
  le corta la sesión en la request siguiente, sin esperar a que venza la cookie.

### En el front

- **No hay zonas públicas.** `/login` es la única ruta sin sesión.
- Sin sesión, cualquier ruta redirige a `/login` guardando la ruta original;
  al autenticarse se vuelve ahí, no al home.
- Cualquier `401` de cualquier llamada tira la sesión abajo y rebota al login.

## Cuenta root inicial

Se crea al arrancar **solo si no existe ninguna cuenta root**. Por defecto
`root` / `root` / `test@test.com`, configurable por `Semilla__Root__*`.

Nunca pisa una cuenta root existente: una vez creada, la contraseña se cambia desde el ABM
y las variables de entorno dejan de tener efecto.

> La contraseña `root` tiene 4 caracteres y el ABM exige 8. Es a propósito: la semilla no
> pasa por la validación porque es para pruebas. Cambiala antes de usar el sistema en serio.

## Lo que todavía no está

- Permisos finos. Hoy el rol es la unidad de autorización; `supervisor` y `vendedor`
  existen pero no tienen ningún endpoint propio.
- Puntos de venta. La franja de color del layout está fija en el local 1.
- Recuperación de contraseña por mail.
- Auditoría de quién creó o modificó cada usuario (`created_by` / `updated_by`).
